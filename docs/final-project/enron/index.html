Midterm Vignette

As mentioned in class during Week 7, this dataset was actually the first dataset brainstormed among the instructors for pre-approved Midterm \(\rightarrow\) Final Project purposes! We mention this here because, it represents a rare instance where we can actually analyze real data from a real company’s backend DB, rather than having to simulate it (as in the healthcare example).

The most widely-studied version of this dataset contains about 500,000 emails, released to the public as part of the litigation over Enron’s prosecution for accounting fraud by the US Federal Bureau of Investigation and Federal Energy Regulatory Commission.

As mentioned on the main datasets page, however, the goal here is not to analyze the Enron emails as such, but to imagine how you would handle new email data continuously streaming into an OLTP database with the same structure! In other words, your analysis of this data should be generalizable to other organizations with significantly fewer (or significantly more) employees.

Your task here takes inspiration from a 2015 analysis of the Enron corpus which discovered a set of NLP-based features that could be extracted from the text of the emails which, in turn, predicted with high accuracy both the gender and the level in an organizational chart of the email-writers. Even within a single 3-email thread, for example, features of language usage already start to emerge, as shown in Figure 1. These individual-thread inferences can then be aggregated over the hundreds of thousands of available emails to obtain detailed information about the communicative “culture” within an organization.

You have been hired as a data scientist at an organization (which was impressed by your big data and cloud computing skills!) which has recently recived concerning reports from HR about an overall “toxic culture” when it comes to day-to-day interactions between genders and between higher- and lower-level employees. The organization has heard about how Google’s “Project Oxygen” reduced tensions between managers and employees, and is hoping you can use their email corpus to identify issues and achieve a similar outcome.

As you can read in Prabhakaran (2015), there are straightforward NLP-based features that can be extracted at the end of the data-processing pipeline, measuring aspects of the emails like politeness or gendered adjectives (“bossy” vs. “confident”). Your job here is thus to tackle the infrastructural challenges that lay “along the way” to these measurable outcomes:

  • First, the organization would like a well-organized [but internal!] interface like enron-mail.com where they can browse individual emails which may be of concern
  • The organization would also like this interface to have a feature where one can click on an individual’s name, or the name of a department, to see a “profile” of the extracted NLP features for that individual or department
  • Finally, the organization would like a live dashboard where they can see essentially a “heatmap” of their different departments, based on the volume of emails being sent between members of each department over the past 24 hours.

Question 1 Starter: OLTP Structure

Here, the OLTP structure used by the organization to record email information is similar to the logs of any other SMTP email server: Sort of like the examples of HTTP and Linux logs we saw in class during Week 1, each event or record represents information about an incoming or outgoing email. The following records illustrate the types of issues which may arise in bringing these records from “raw” OLTP form into an OLAP infrastructure.

First, this email (randomly sampled from the folder containing Kenneth Lay’s inbox) illustrates a “well-formatted” email, where fields like Date, Subject, From, and To, as well as the plaintext email body, would be easy to parse and enter into an OLAP framework (such as a data warehouse or data lake):

As part of handling these email records, the following metadata file collects the names of each “Person of Interest” (POI) during the fraud hearings, including the list of emails found in the corpus for each POI:

Code 
import polars as pl
import itables

enron_meta_pl = pl.read_parquet('enron_meta.parquet')
itables.show(enron_meta_pl)
Loading ITables v2.8.1 from the internet... (need help?)

Note that, although it is not the most efficient way to store the person-to-email mappings, the Parquet format does support typed Lists, as we can see by calling Polars’ read_parquet_schema() function on the metadata file displayed above:

Code 
import polars as pl

pl.read_parquet_schema('enron_meta.parquet')
Schema([('name', String),
        ('last', String),
        ('first', String),
        ('emails', List(String)),
        ('verdict', String),
        ('source', String)])
